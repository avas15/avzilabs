# Data platform engineering — worked demo

A self-contained demonstration of how I build data products end to end:
ingestion from messy sources → entity resolution → a provenance-tracked
warehouse layer → quality gates → an application on top.

**The domain is synthetic.** It models airport landing-slot allocation, chosen
as a *structural* analogue of the regulated-asset platform I run in my day job:
slot allocation rounds behave like auctions, slot leases like licences, carriers
like operators, airports like markets. Nothing in this repository derives from
client work — see [Sanitisation](#sanitisation).

├── data/
│   ├── build_demo_db.py     seeded synthetic warehouse generator
│   └── demo.sqlite          generated (8 tables, 3 views, ~15k panel rows)
├── etl/

## Quick start

```bash
python data/build_demo_db.py            # build the warehouse (deterministic)
python etl/pipeline_demo.py --dry-run   # show what would change, write nothing
python etl/pipeline_demo.py             # run it
python etl/news_updater.py              # poll the external feed
python -m http.server 8777 --directory site
```

Then open <http://localhost:8777>. Only the standard library is required; the
page pulls Chart.js from a CDN and degrades to tables if that's unavailable.

## What each piece demonstrates

### `data/build_demo_db.py` — schema and generation
A normalised schema with reference tables, a fact table for allocation outcomes,
a holdings table with terms and expiry, and a **long-format panel**
(`carrier_panel_obs`) keyed by
`(entity, market, metric, period, period_type, source, quality_flag, vintage)`.

That key is the point. It means a new data vintage **appends rather than
overwrites**, two sources reporting the same metric **coexist instead of
colliding**, and annual and quarterly figures never overwrite each other. Getting
this key wrong is one of the most common and most damaging data-modelling
mistakes — it silently destroys history and nobody notices for months.

Seeded RNG throughout, so output is byte-identical across runs.

### `etl/pipeline_demo.py` — the pipeline
Six properties, each deliberate and each exercised by the code:

| Property | Implementation |
|---|---|
| Run lock | Single-run guarantee; stale locks reclaimed after a TTL so a killed process can't wedge the pipeline |
| Fail safe | Unreachable source → step marked `degraded`, run exits cleanly, last-good data untouched. Never half-writes |
| Idempotent | Upserts on a natural key including source and vintage; re-running changes nothing |
| Change detection | Cheap manifest diff and fingerprint first; expensive detail fetch only for records that actually moved |
| Stage then swap | Derived tables built in staging, promoted in one transaction — readers never see a partial state |
| Provenance | Every step appends to `run_manifest` with rows-in/rows-out, so any figure in the product traces to a run |

Try the failure path — it's the most important one:

```bash
python etl/pipeline_demo.py --simulate-outage
```

```
[DEGR] change_detect   upstream allocation registry unreachable; last-good data retained
source degraded — exiting cleanly, last-good data intact
```

A pipeline that fails loudly and leaves yesterday's good data in place is worth
more than one that silently publishes a partial today.

### `etl/news_updater.py` — scheduled external feed
Polls Wikipedia's public REST API (openly licensed, CC BY-SA, and deliberately
unrelated to any client domain). Demonstrates ETag / `If-None-Match`
revalidation — an unchanged poll costs one 304 and no parsing — content hashing
to distinguish "fetched again" from "actually changed", upsert on a stable id,
and cache-backed degradation when offline (`--offline`).

### `site/index.html` — the application layer
A dependency-light single page: KPI tiles, a multi-source trend chart, share
donut, clearing-price and expiry-profile charts, and a league table, all driven
by the generated extract. Responsive, theme-aware, and — the design point —
**overlapping sources are plotted as separate lines rather than blended**, with
headline figures labelled by origin.

## Data quality

The pipeline runs six assertions on every execution and exits non-zero if any
fail: orphaned leases, expiry before start, negative slot counts, awarded
exceeding offered, percentage metrics outside `[0,1]`, and a non-empty panel.

## Sanitisation

- The domain is a structural analogue, not a disguise. Slot allocation genuinely
  differs from the client domain in entities, units and economics.
- All data is generated from a seeded RNG in `build_demo_db.py`. No real
  figures, entities or geographies appear.
- Table and column names are original to this demo. No production schema,
  identifier or naming convention is reproduced.
- Carriers, airports and groups are invented and do not correspond to real
  organisations.
- Client systems are described elsewhere only at the level of engineering
  approach — no code, data or schema.
- The external feed is a public, openly licensed API.

## Notes

Deliberately unglamorous choices worth calling out: SQLite rather than a
warehouse, because the demo should run anywhere in under a second; no framework
on the front end, because the interesting work is upstream; and a seeded
generator rather than a committed dump, so the data is reproducible and
reviewable rather than opaque.

See `docs/` for the architecture decision records.
