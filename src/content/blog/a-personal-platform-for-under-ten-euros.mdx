I wanted one place to put everything: portfolio, writing, a few live application demos,
multiplayer games to play with friends, and a set of private file tools. The constraint was that
the whole thing had to cost less than a takeaway per month, and that a traffic spike on a game
must not be able to take down the blog.

The site and word game now run on Cloudflare. The small server and file workers described
below are the plan for the next stage.

## The metered billing problem

The obvious route is a small cloud instance. The catch is not the instance price, it is egress.
Bandwidth on the major clouds is billed per gigabyte, and a browser game or a WebGL build is
tens of megabytes per visitor.

An app can keep working while its bandwidth bill grows. Alerts help, but they do not
necessarily stop usage. I want a budget I can enforce before the invoice arrives.

A monthly server price makes compute costs predictable, but it does not cap the whole bill.
Hetzner charges for traffic above the included allowance, and its cost alerts do not stop
spending. The plan needs traffic limits and a way to stop the service before an overage.
See [Hetzner's billing FAQ](https://docs.hetzner.com/cloud/billing/faq/).

## Isolation you cannot buy with tuning

The second requirement was harder. If the games and the blog share a machine, then a busy game
degrades the blog. You can mitigate that with resource limits, and you should, but limits only
go so far.

Memory limits and CPU weighting help services share a machine. They still share its network
capacity, so a busy service can affect the others unless traffic is controlled too.

So I stopped trying to solve it on the machine.

The public site is entirely static and served from a CDN. It will not share the application
server's CPU, memory or network connection. A busy conversion worker therefore won't consume
the resources serving the blog.

## The shape it settled into

The static site carries the blog, the portfolio, and the landing pages for every game and tool.
Those are the pages that need to be fast and indexed, and they are the ones that will get
traffic if anything ever does well.

The plan is to use one small server for BidSim's WebSocket sessions, the file-conversion queue
and live application demos. Each service will have resource limits. An outbound tunnel and
private administration will keep origin ports closed; the public apps will still need their
own access controls.

Large static downloads will stay off the application server. Storage and request charges
will need their own limits, even where downloads have no egress charge.

## Two things worth stealing

**Serve static downloads separately.** A popular download should not compete with a live
auction for the same server connection.

**Budget for the whole service.** The monthly instance price is only the starting point.
Include tax, IP addresses and storage, then decide what should stop when usage reaches the limit.

## On running the media tools locally

The plan for heavier media conversion is a machine at home that pulls jobs over an outbound
connection. The interface will show the worker as offline when that machine is switched off.

Partly this is about cost, since transcoding could exhaust a small server. Jobs that depend
on a residential network connection also behave differently from those on a datacenter
network, which affects where those workers can run.
